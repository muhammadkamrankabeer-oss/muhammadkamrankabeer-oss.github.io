#01
LinuxServer

Linux vs Windows Server

Linux dominates production because it's open, auditable, lightweight, and fully scriptable. Windows Server costs licensing fees and hides complexity behind GUIs that can't be automated at scale.

# Check OS and kernel uname -a cat /etc/os-release # Linux process list — clean, scriptable ps aux | grep nginx

📘 Definition
Linux is an open-source operating system kernel. Linux Server refers to running Linux distributions like Ubuntu or Debian to serve applications, websites, and databases in production environments.

💡 Why It Matters
Over 90% of cloud servers run Linux. Knowing Linux means you can manage any cloud VM, container, or CI runner — it's the foundation of every DevOps role.

🌍 Real Example
A DevOps engineer SSHs into an Ubuntu EC2 instance, checks nginx logs with journalctl, and restarts the service with systemctl restart nginx — all from the terminal.

💻 Code/Command/Example
uname -r — shows the running kernel version. cat /etc/os-release — shows distro info.

🎯 Interview Tip
Be ready to compare Linux vs Windows Server on licensing cost, automation capability, performance overhead, and community support.

📝 Practice Exercise
Boot a Linux VM, run uname -a and df -h, then compare the output with Windows Task Manager equivalents.

#02
LinuxFoundation

Why Linux Matters in DevOps

Every cloud VM, Docker container, CI runner, and Kubernetes node runs Linux. Linux fluency is the baseline that unlocks the entire DevOps stack. No shortcuts — this is the foundation.

systemctl status nginx journalctl -u nginx --since "1 hour ago" ss -tlnp | grep :80 chmod 640 /etc/nginx/nginx.conf

📘 Definition
Linux is the OS that runs Docker containers, Kubernetes pods, CI/CD agents, and virtually every cloud server. Without Linux skills, you can't operate any modern DevOps toolchain effectively.

💡 Why It Matters
When a deployment fails at 2 AM, you need to SSH in, read logs, check processes, and fix config files — all from a terminal. Linux is the language of production systems.

🌍 Real Example
A junior DevOps engineer uses ss -tlnp to verify nginx is listening on port 80, then journalctl -u nginx to trace a 502 error back to a misconfigured upstream.

💻 Code/Command/Example
systemctl restart nginx — restart a service. tail -f /var/log/syslog — live log watching.

🎯 Interview Tip
Be ready to demonstrate: checking service status, reading logs, modifying file permissions, and managing processes without a GUI.

📝 Practice Exercise
Install nginx on a Linux VM. Stop it, start it, check its logs, and change its port — using only the terminal.

#03
LinuxAutomation

Automating DevOps Workstations

A fully automated workstation setup means rebuilding your entire dev environment in under 10 minutes on any machine. Script it once, version-control it, run it anywhere.

#!/bin/bash TOOLS=("git" "docker.io" "ansible" "terraform") for pkg in "${TOOLS[@]}"; do apt-get install -y $pkg && echo "✓ $pkg" done

📘 Definition
Workstation automation means using Bash scripts or Ansible playbooks to install and configure all required DevOps tools — git, Docker, Ansible, Terraform, VS Code, etc. — automatically and repeatably.

💡 Why It Matters
Manual tool installation wastes time, introduces inconsistencies, and can't be reviewed or version-controlled. An automated setup is reproducible and shareable across a team.

🌍 Real Example
Kamran keeps a setup.sh script in Git. On a fresh Xubuntu install, one command provisions his entire DevOps workstation in minutes.

💻 Code/Command/Example
chmod +x setup.sh && ./setup.sh — run your workstation bootstrap script.

🎯 Interview Tip
Mention idempotency — your script should be safe to run multiple times without breaking anything. This is where Ansible shines over raw bash.

📝 Practice Exercise
Write a Bash script that installs git, docker, and ansible on a fresh Ubuntu VM, then verify each tool is available with --version.

Building Labs on Old Hardware

You don't need expensive servers. An old laptop or refurbished Dell with 8–16GB RAM runs a full DevOps lab — Linux, Docker, Ansible, and a monitoring stack simultaneously.

free -h # RAM available nproc # CPU cores df -h / # Disk space # 8GB RAM = full DevOps lab possible

📘 Definition
A homelab is a personal server environment built on consumer or refurbished hardware where you practice real infrastructure skills without cloud costs.

💡 Why It Matters
Hands-on lab experience is what separates engineers who understand tools from those who've only read about them. Old hardware gives you unlimited practice time.

🌍 Real Example
A Dell Latitude E7440 with 8GB RAM runs Xubuntu + Docker + Ansible control node + Prometheus stack — a full working DevOps environment at zero cloud cost.

💻 Code/Command/Example

🎯 Interview Tip

📝 Practice Exercise

#05
LinuxHomelab

DevOps Homelab Architecture

A well-designed homelab mirrors production: a control node runs Ansible, target VMs simulate servers, Docker runs services, monitoring watches everything. Same tools, smaller scale.

control-node 192.168.1.10 ├── Ansible + Terraform server-01 192.168.1.11 └── Docker + Compose apps monitor-01 192.168.1.12 └── Prometheus + Grafana

📘 Definition
A homelab architecture is the deliberate design of your practice environment — assigning roles to machines and networking them together so they mirror how real production infrastructure is organised.

💡 Why It Matters
Random experimentation teaches less than structured practice. A designed homelab forces you to think about networking, separation of concerns, and monitoring — just like a real job.

🌍 Real Example
Control node runs ansible-playbook over SSH to configure server-01, while monitor-01 scrapes metrics from both. This is exactly how production Ansible + Prometheus works.

💻 Code/Command/Example
ansible -i inventory all -m ping — verify all lab nodes are reachable from your control node.

🎯 Interview Tip
Be ready to draw your homelab architecture from memory and explain each component's role and how they communicate.

📝 Practice Exercise
Create an Ansible inventory file listing 2 VMs, then run a ping module to verify connectivity from your control node.

#06
DockerBasics

What is Docker?

Docker packages your application and all its dependencies into a container — a lightweight, portable unit that runs identically on any machine. No more "works on my laptop".

docker run -d -p 80:80 --name web nginx docker ps docker logs web --follow docker exec -it web bash

📘 Definition
Docker is a containerisation platform that bundles an application with its runtime, libraries, and config into a single portable image. Containers are isolated processes sharing the host OS kernel.

💡 Why It Matters
Containers eliminate environment inconsistencies. The same image runs on your laptop, a CI server, and a Kubernetes cluster — making deployments predictable and repeatable.

🌍 Real Example
A team ships a Node.js app as a Docker image. The same docker run command works on a developer's Mac, Ubuntu CI runner, and AWS EC2 instance without any environment changes.

💻 Code/Command/Example
docker ps — list running containers. docker images — list local images. docker stop web — stop a container.

🎯 Interview Tip
Explain the difference between an image (read-only template) and a container (running instance of an image). This is a common first Docker question.

📝 Practice Exercise
Run docker run -d -p 8080:80 nginx, open http://localhost:8080 in a browser, then use docker logs and docker exec to explore the running container.

#07
DockerVMs

Docker vs Virtual Machines

VMs virtualise hardware — each gets its own OS kernel eating GBs of RAM. Docker containers share the host kernel and start in milliseconds. For microservices, Docker wins on density and speed.

VM: App → Guest OS → Hypervisor → Host OS Con: App → Docker Engine → Host OS Startup: VM=60s Container=<1s RAM: VM=2GB Container=50MB

📘 Definition
A VM runs a full guest OS on top of a hypervisor. A container shares the host kernel and only packages the app and its dependencies — much lighter and faster to start.

💡 Why It Matters
Choosing between VMs and containers impacts cost, boot time, density, and isolation. Most modern workloads run containers inside VMs — combining both strengths.

🌍 Real Example
An AWS EC2 instance (VM) hosts 20 Docker containers serving different microservices. The VM provides isolation from other tenants; containers provide fast, dense app deployment.

💻 Code/Command/Example
docker stats — see real-time CPU/RAM usage per container, demonstrating how lightweight they are versus a full VM.

🎯 Interview Tip
Know when VMs are still preferred: strong security isolation, running different OS kernels, or legacy applications that don't containerise easily.

📝 Practice Exercise
Run 5 nginx containers with docker run and check total RAM usage with docker stats. Compare to what 5 VMs would cost in RAM.

#08
DockerStorage

Docker Volumes

Containers are ephemeral — kill one and its filesystem is gone. Volumes are persistent storage managed by Docker, surviving container restarts, removals, and recreations.

version: '3.9' services: postgres: image: postgres:15 volumes: - pgdata:/var/lib/postgresql/data volumes: pgdata: # named — Docker managed

📘 Definition
Docker volumes are persistent storage areas outside the container filesystem. They survive container deletion and can be shared between containers. Types: named volumes (Docker-managed), bind mounts (host paths), tmpfs (memory-only).

💡 Why It Matters
Without volumes, database data, uploaded files, and log outputs are lost every time a container is removed or updated. Volumes are essential for stateful workloads.

🌍 Real Example
A PostgreSQL container uses a named volume for /var/lib/postgresql/data. When the container is upgraded to a newer Postgres version, the data volume remains intact.

💻 Code/Command/Example
docker volume ls — list all volumes. docker volume inspect pgdata — see volume details and mount path.

🎯 Interview Tip
Know the difference: named volumes are managed by Docker (preferred for databases), bind mounts map a specific host directory (useful for development).

📝 Practice Exercise
Run a Postgres container with a named volume, insert data, remove the container, start a new one with the same volume, and verify the data persists.

#09
DockerNetworking

Docker Networking

Containers need to communicate — with each other, the host, and the internet. Docker provides network drivers for each use case: bridge, host, overlay, and none.

docker network create app-net docker run -d --network app-net --name api myapi docker run -d --network app-net --name db postgres # api resolves db by container name: db:5432 docker network inspect app-net

📘 Definition
Docker networking allows containers to communicate. bridge — default isolated network for containers on one host. host — shares host network stack. overlay — spans multiple Docker hosts (Swarm/Kubernetes). none — no network.

💡 Why It Matters
Proper networking keeps services isolated (security) while letting them communicate (functionality). Misconfigurations expose services to the internet or break inter-container communication.

🌍 Real Example
An API container and a Postgres container are on the same bridge network called app-net. The API connects to Postgres using the hostname db — no IP address needed.

💻 Code/Command/Example
docker network ls — list all networks. docker network inspect bridge — see which containers are connected.

🎯 Interview Tip
Explain DNS resolution in Docker networks — containers on the same user-defined bridge network can reach each other by container name. This is a common interview scenario.

📝 Practice Exercise
Create a custom bridge network, run two containers on it, exec into one, and ping the other by name to confirm DNS resolution works.

#10
DockerBest Practices

Docker Mistakes Beginners Make

Most Docker production problems come from the same repeated mistakes: running as root, using :latest tags, ignoring .dockerignore, storing state in containers, and fat images.

# ❌ Bad FROM ubuntu:latest COPY . . # ✅ Good FROM python:3.11-slim COPY requirements.txt . RUN pip install -r requirements.txt USER appuser

📘 Definition
Common Docker mistakes that cause security vulnerabilities, bloated images, and production instability — all avoidable with a few best practices.

💡 Why It Matters
Running containers as root, using :latest tags, or storing data inside containers are the three most common causes of Docker security incidents and deployment failures.

🌍 Real Example
A team's pipeline breaks because :latest pulled a new base image with a breaking change. Pinning to python:3.11.9-slim would have prevented it entirely.

💻 Code/Command/Example
docker scan myimage or trivy image myimage — scan your image for known CVEs before shipping.

🎯 Interview Tip
Top 5 mistakes: (1) using root user, (2) :latest tags, (3) no .dockerignore, (4) storing data in containers, (5) single-stage builds with dev dependencies included.

📝 Practice Exercise
Take an existing Dockerfile, apply multi-stage build, add a non-root USER, pin the base image tag, and add a .dockerignore. Compare image sizes before and after.

#11
AWSCompute

What is AWS EC2?

EC2 (Elastic Compute Cloud) is AWS's virtual server service. Pick the CPU, RAM, and OS — AWS runs it. Pay per second. Scale from one instance to thousands in minutes.

aws ec2 run-instances \ --image-id ami-0c55b159cbfafe1f0 \ --instance-type t3.micro \ --key-name my-key \ --security-group-ids sg-12345 ssh -i my-key.pem ubuntu@PUBLIC_IP

📘 Definition
EC2 (Elastic Compute Cloud) provides resizable virtual machines in AWS. You choose the instance type (CPU/RAM ratio), OS AMI, storage, and network settings. You pay per second of usage.

💡 Why It Matters
EC2 is the foundation of most AWS architectures. Understanding instance types, AMIs, security groups, and key pairs is required for any cloud role.

🌍 Real Example
A startup hosts their Django app on a t3.medium EC2 instance with an Elastic IP. When traffic spikes, they launch additional instances behind an ALB using an Auto Scaling Group.

💻 Code/Command/Example
aws ec2 describe-instances --query "Reservations[*].Instances[*].PublicIpAddress" — list all public IPs of running instances.

🎯 Interview Tip
Know the difference between On-Demand (pay per second), Reserved (1-3 year discount), Spot (up to 90% cheaper, can be interrupted), and Savings Plans.

📝 Practice Exercise
Launch a free-tier t3.micro EC2 instance, SSH into it, install nginx, and access it via the public IP. Terminate it when done.

#12
AWSNetworking

What is a VPC?

A VPC (Virtual Private Cloud) is your private network inside AWS. You define the IP range, create public and private subnets, control routing, and decide what reaches the internet.

VPC: 10.0.0.0/16 ├── Public: 10.0.1.0/24 ← web+NAT │ ├── EC2 (web server) │ └── NAT Gateway └── Private: 10.0.2.0/24 ← app+db ├── EC2 (app server) └── RDS (database)

📘 Definition
A VPC is an isolated virtual network in AWS. Key components: subnets (public/private), Internet Gateway (public internet access), NAT Gateway (private subnet outbound), Route Tables, and Security Groups.

💡 Why It Matters
Every production AWS workload lives inside a VPC. Understanding VPC architecture is essential for security — databases should always be in private subnets, unreachable from the internet.

🌍 Real Example
A 3-tier app: web servers in public subnets (reachable via ALB), app servers and RDS in private subnets (reachable only from web tier), with a NAT Gateway for outbound updates.

💻 Code/Command/Example
aws ec2 describe-vpcs — list your VPCs. aws ec2 describe-subnets — list subnets and their availability zones.

🎯 Interview Tip
Be ready to design a VPC from scratch on a whiteboard: CIDR block, public/private subnets across 2 AZs, IGW, NAT Gateway, and Security Group rules.

📝 Practice Exercise
Using Terraform or the AWS console, create a VPC with one public and one private subnet. Launch an EC2 in each. Verify only the public one is internet-reachable.

#13
AWSLoad Balancer

Load Balancer Explained

A load balancer distributes incoming traffic across multiple servers so no single instance gets overwhelmed. AWS ALB (Application Load Balancer) works at Layer 7 — routing by URL path, headers, and hostnames.

Client → ALB (port 443) ├── /api/* → Target Group A ├── /app/* → Target Group B └── /* → Target Group C Health Check: GET /health → 200 OK

📘 Definition
Load balancers distribute traffic across healthy backend targets. AWS offers: ALB (Layer 7, HTTP/HTTPS, path-based routing), NLB (Layer 4, TCP/UDP, ultra-low latency), and CLB (legacy, avoid for new projects).

💡 Why It Matters
Without a load balancer, one EC2 instance handles all traffic. A single failure takes down your entire application. Load balancers enable high availability and horizontal scaling.

🌍 Real Example
An e-commerce site uses an ALB to route /api/* to backend EC2s and /static/* to an S3 origin via CloudFront — all managed from one DNS entry.

💻 Code/Command/Example
aws elbv2 describe-load-balancers — list all load balancers. aws elbv2 describe-target-health — check target health status.

🎯 Interview Tip
ALB = Layer 7 (HTTP routing, SSL termination, WAF). NLB = Layer 4 (TCP, static IPs, extreme throughput). Know when to use each.

📝 Practice Exercise
Create an ALB with two target groups. Route /api requests to one group and all other requests to another. Test with curl.

#14
CloudNginx

Reverse Proxy vs Load Balancer

Both sit in front of your servers — but serve different roles. A reverse proxy handles SSL termination, caching, and routing. A load balancer distributes traffic across backend instances.

# nginx as reverse proxy server { listen 443 ssl; server_name api.devriston.com.pk; location / { proxy_pass http://localhost:3000; proxy_set_header Host $host; } }

📘 Definition
A reverse proxy sits in front of one or more servers and forwards client requests — handling SSL, caching, compression, and request routing. A load balancer distributes traffic across multiple identical backend instances for scalability.

💡 Why It Matters
Nginx is often both simultaneously — acting as a reverse proxy for SSL termination while also load-balancing across upstream app servers. Understanding both roles clarifies why nginx config looks the way it does.

🌍 Real Example
Nginx terminates SSL for devriston.com.pk, then proxies requests to a Node.js backend on port 3000. If multiple Node instances run, nginx upstream block distributes load.

💻 Code/Command/Example
nginx -t — test config syntax. systemctl reload nginx — apply config changes without downtime.

🎯 Interview Tip
Key distinction: reverse proxy is about content transformation and forwarding (one backend); load balancer is about traffic distribution (multiple identical backends).

📝 Practice Exercise
Configure nginx as a reverse proxy for a local Node.js app. Add SSL using a self-signed cert. Verify HTTPS works in the browser.

#15
AWSArchitecture

High Availability Basics

HA means your system keeps running even when individual components fail. The core principle: eliminate single points of failure. Deploy across multiple AZs. Use health checks and auto-recovery.

HA Architecture — 2 AZ ALB / \ AZ-1 AZ-2 EC2 EC2 RDS ←→ RDS (primary) (standby) Failover: automatic. RTO: ~60s

📘 Definition
High Availability (HA) is the design principle of building systems that continue operating despite component failures. Measured as uptime percentage — 99.9% = ~8.7 hours downtime/year; 99.99% = ~52 minutes/year.

💡 Why It Matters
Every single-server deployment is a single point of failure. HA architecture means a failed EC2, AZ outage, or database crash doesn't bring down the whole service.

🌍 Real Example
RDS Multi-AZ keeps a standby replica in a second AZ. If the primary fails, AWS automatically promotes the standby — applications reconnect within ~60 seconds.

💻 Code/Command/Example
aws rds describe-db-instances --query "DBInstances[*].MultiAZ" — verify Multi-AZ is enabled on your RDS instances.

🎯 Interview Tip
HA checklist: multi-AZ deployment, load balancer with health checks, auto-scaling group, read replicas/Multi-AZ for DB, S3 for static assets, Route53 health checks.

📝 Practice Exercise
Design on paper a 2-AZ HA architecture for a Django app on AWS. Include ALB, EC2 Auto Scaling Group, RDS Multi-AZ, and S3 for static files.

#16
TerraformIaC

Infrastructure as Code

IaC means your servers, networks, and cloud resources are defined in code files — not manually configured. Reproducible, reviewable in Git, and deployable in minutes — not days.

resource "aws_instance" "web" { ami = "ami-0c55b159cbfafe1f0" instance_type = "t3.micro" tags = { Name = "devriston-web" ManagedBy = "terraform" } }

📘 Definition
Infrastructure as Code (IaC) is the practice of managing and provisioning infrastructure through machine-readable config files rather than manual processes. Terraform is the most widely used IaC tool.

💡 Why It Matters
Manual infrastructure is error-prone, slow, and undocumented. IaC means your entire cloud environment is version-controlled, peer-reviewed, and can be rebuilt in minutes after a disaster.

🌍 Real Example
Instead of clicking through the AWS console to create a VPC, EC2, RDS, and ALB, a DevOps engineer runs terraform apply and the full 3-tier environment is ready in 4 minutes.

💻 Code/Command/Example
terraform init → terraform plan → terraform apply — the standard Terraform workflow for every infrastructure change.

🎯 Interview Tip
IaC benefits: consistency, speed, disaster recovery, code review for infra changes, environment replication (dev/staging/prod from same code).

📝 Practice Exercise
Write a Terraform config that creates an S3 bucket with versioning enabled. Run terraform plan to preview, terraform apply to create, then terraform destroy to clean up.

#17
TerraformMulti-Cloud

Why Terraform Matters

Terraform is cloud-agnostic. Write infrastructure for AWS today, replicate on GCP or Azure tomorrow with minimal changes. 3000+ providers cover everything from DNS to Kubernetes to GitHub.

terraform init # download providers + modules terraform plan # show what will change terraform apply # execute the changes + aws_instance.web will be created Plan: 2 to add, 0 to change, 0 to destroy.

📘 Definition
Terraform uses a declarative HCL (HashiCorp Configuration Language) to describe desired infrastructure state. It works across AWS, GCP, Azure, and 3000+ other providers via a plugin system.

💡 Why It Matters
Unlike CloudFormation (AWS-only), Terraform lets you manage multi-cloud and hybrid environments with one tool and one skill set — making it the industry standard for IaC.

🌍 Real Example
A company uses Terraform to manage AWS infrastructure, Cloudflare DNS, and GitHub repo settings — all from the same codebase and workflow.

💻 Code/Command/Example
terraform show — display current state. terraform state list — list all managed resources. terraform output — show output values.

🎯 Interview Tip
Terraform vs CloudFormation: Terraform = multi-cloud, HCL, open-source, large community. CloudFormation = AWS-only, JSON/YAML, native AWS integration, no state management needed.

📝 Practice Exercise
Create a Terraform config with an AWS and a Cloudflare provider. Provision one resource from each. Observe how terraform plan handles both in one run.

#18
TerraformState

Terraform State

Terraform tracks what it has built in a state file. This is how it knows what exists, what changed, and what to destroy. Never commit state to Git — use remote backends like S3 with DynamoDB locking.

terraform { backend "s3" { bucket = "devriston-tf-state" key = "prod/terraform.tfstate" region = "us-east-1" dynamodb_table = "tf-lock" encrypt = true } }

📘 Definition
Terraform state is a JSON file (terraform.tfstate) that maps your HCL config to real cloud resources. It's Terraform's source of truth for what exists, what changed, and what needs updating.

💡 Why It Matters
Without proper state management, two engineers running terraform apply simultaneously can corrupt infrastructure. Remote state with locking prevents this.

🌍 Real Example
A team stores state in S3 with encryption and uses DynamoDB for state locking. When one engineer runs terraform apply, the lock prevents anyone else from modifying state simultaneously.

💻 Code/Command/Example
terraform state list — view all tracked resources. terraform state show aws_instance.web — inspect a specific resource in state.

🎯 Interview Tip
Never commit terraform.tfstate to Git — it contains sensitive data (passwords, keys). Always use remote backends (S3/GCS/Terraform Cloud) with encryption and state locking.

📝 Practice Exercise
Set up an S3 backend for your Terraform state. Run terraform init to migrate local state to S3, then verify the state file appears in the bucket.

#19
AnsibleAutomation

What is Ansible?

Ansible automates server configuration over SSH — no agent required. Write a playbook in YAML, run it against 1 or 1000 servers, get the same result every time. Idempotent by design.

- name: Install and start Nginx hosts: webservers become: true tasks: - apt: name=nginx state=present - service: name=nginx state=started enabled=yes

📘 Definition
Ansible is an agentless automation tool that uses SSH to configure servers, deploy applications, and orchestrate tasks. Playbooks are written in YAML and executed sequentially against inventory hosts.

💡 Why It Matters
Terraform provisions infrastructure; Ansible configures it. After terraform apply creates your EC2 instances, Ansible installs packages, writes config files, and starts services — automatically.

🌍 Real Example
A playbook installs nginx, copies a config template with Jinja2 variables, enables the service, and reloads it — all in one idempotent run that's safe to re-execute any time.

💻 Code/Command/Example
ansible-playbook -i inventory site.yml — run a playbook. ansible all -m ping -i inventory — test connectivity to all hosts.

🎯 Interview Tip
Key distinction: Terraform = infrastructure provisioning (VMs, networks, S3). Ansible = configuration management (install packages, manage files, start services). They complement each other.

📝 Practice Exercise
Write an Ansible playbook that installs nginx, copies an index.html file, and starts the service. Run it against a VM and verify nginx serves your file.

CI/CDGitHub Actions

What is CI/CD?

CI (Continuous Integration) automatically tests every code push. CD (Continuous Delivery/Deployment) automatically deploys passing builds. Together they eliminate manual releases and catch bugs early.

on: [push] jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: npm install && npm test - run: docker build -t myapp .

📘 Definition
CI — every code commit triggers automated tests, lint, and build checks. Catches integration bugs immediately. CD — passing CI builds are automatically deployed to staging or production without manual steps.

💡 Why It Matters
Manual deployments are slow, error-prone, and undocumented. CI/CD means every merge to main is automatically tested and shipped — with a full audit trail in Git.

🌍 Real Example
Developer pushes to GitHub → Actions runs tests → builds Docker image → pushes to ECR → deploys to ECS. Total time: 4 minutes. Zero manual steps.

💻 Code/Command/Example
gh run list — list recent GitHub Actions runs. gh run view RUN_ID — inspect a specific pipeline run.

🎯 Interview Tip
CI = detect problems fast (tests, lint, security scan on every push). CD = ship fast (auto-deploy to staging, manual gate to production). Know the difference and when each applies.

📝 Practice Exercise
Create a GitHub Actions workflow that runs on push, executes a test command, and builds a Docker image. Push a bad commit and watch the pipeline fail.

#21
CI/CDDocker

GitHub Actions CI/CD Pipeline

GitHub Actions is the most popular CI/CD tool today — it's free for public repos, deeply integrated with GitHub, and has thousands of community actions for every task.

- name: Build and push Docker image run: | docker build -t $ECR_REPO:$SHA . docker push $ECR_REPO:$SHA - name: Deploy to ECS uses: aws-actions/amazon-ecs-deploy-task-definition@v1

📘 Definition
GitHub Actions workflows are YAML files in .github/workflows/ that run on triggers (push, PR, schedule). Jobs contain steps that run commands or reuse published Actions.

💡 Why It Matters
GitHub Actions is tightly integrated with your code — no separate CI server to manage. It's the standard for open-source DevOps portfolios and increasingly for enterprise workloads.

🌍 Real Example
Devriston's Samba4 project uses GitHub Actions to run YAML lint, Ansible lint, syntax check, and Checkov security scan on every pull request before merge.

💻 Code/Command/Example
act — run GitHub Actions locally for testing before pushing. Install with brew install act or download the binary.

🎯 Interview Tip
Know the structure: on (triggers), jobs (parallel groups), steps (sequential commands/actions), env (variables), secrets (sensitive values).

📝 Practice Exercise
Add a GitHub Actions workflow to an existing repo that runs ansible-lint and yamllint on every push to main. Check the Actions tab to see the results.

#22
CI/CDAnsible

Ansible Roles Structure

Ansible roles are the standard way to organise complex playbooks. Each role has a fixed directory structure — tasks, handlers, templates, defaults, and vars — making automation modular and reusable.

roles/nginx/ ├── tasks/main.yml # what to do ├── handlers/main.yml # restart triggers ├── templates/ # Jinja2 configs └── defaults/main.yml # default vars

📘 Definition
An Ansible role is a self-contained unit of automation with a standardised directory structure. Roles can be shared across projects, published to Ansible Galaxy, and composed together in a playbook.

💡 Why It Matters
Without roles, playbooks become monolithic YAML files that are hard to maintain. Roles enforce separation of concerns — one role per service (nginx, postgres, docker, etc.).

🌍 Real Example

SRE vs DevOps

SRE (Site Reliability Engineering) is Google's implementation of DevOps principles. SREs manage reliability with error budgets, SLOs, and SLAs — using software engineering to solve ops problems.

DNS Fundamentals

DNS (Domain Name System) converts human-friendly domain names like devriston.com.pk into IP addresses. It's the internet's phonebook — every network connection starts with a DNS lookup.

💡 Why It Matters
DNS is involved in every network connection your infrastructure makes. Misconfigured DNS breaks deployments, email, SSL certificates, and inter-service communication.

🌍 Real Example

🎯 Interview Tip
Key record types: A (domain → IPv4), AAAA (domain → IPv6), CNAME (alias), MX (mail), TXT (verification, SPF), NS (nameservers). Know all 6.

A Pod is the smallest deployable unit in Kubernetes. It wraps one or more containers that share network and storage. Pods are ephemeral — controllers (Deployments) manage their lifecycle.

kubectl get pods -A # all namespaces kubectl describe pod web-xyz # pod details kubectl logs web-xyz --follow # live logs kubectl exec -it web-xyz -- bash # shell

📘 Definition
A Pod is a group of one or more containers sharing the same network namespace (IP address) and storage volumes. Kubernetes doesn't manage containers directly — it manages Pods. Deployments manage Pod replicas and rolling updates.

💡 Why It Matters
You rarely create Pods directly in production — you create Deployments that manage Pods for you. Understanding Pods is essential for debugging: kubectl describe pod and kubectl logs are your primary debugging tools.

🌍 Real Example
A web app Deployment maintains 3 Pod replicas. When one Pod crashes, the Deployment controller automatically schedules a replacement on a healthy node — zero manual intervention needed.

💻 Code/Command/Example
kubectl get pods -o wide — see which node each Pod runs on. kubectl delete pod web-xyz — delete a Pod (Deployment will restart it). kubectl top pod — CPU/memory usage.

🎯 Interview Tip
Pod lifecycle states: Pending (scheduling), Running (at least one container running), Succeeded (all containers completed), Failed (all containers exited non-zero), CrashLoopBackOff (container keeps crashing).

📝 Practice Exercise
On a minikube or kind cluster, create a Deployment with 2 replicas of nginx. Delete one Pod and watch Kubernetes recreate it. Use kubectl get pods -w to watch in real-time.

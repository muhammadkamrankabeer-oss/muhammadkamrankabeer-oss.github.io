LinuxServer

Linux vs Windows Server

Linux dominates production infrastructure because it's open, auditable, lightweight, and scriptable. Windows Server costs licensing fees and hides complexity behind GUIs that can't be automated at scale.

# Check OS and kernel
uname -a
cat /etc/os-release

# Linux process list — clean, scriptable
ps aux | grep nginx

# Windows equiv needs GUI or PowerShell
# Get-Process | Where-Object {$_.Name -like "*nginx*"}
  • Cost: Linux is free. Windows Server requires CALs + OS licensing.
  • Automation: Linux is shell-native. Everything is a file or a process.
  • Performance: Linux runs faster on the same hardware with lower memory overhead.
  • DevOps fit: All major DevOps tools (Docker, Ansible, Terraform) are Linux-first.
  • Security: Linux has fewer vulnerabilities and a much smaller attack surface.
#24
LinuxFoundation

Why Linux Matters in DevOps

Every cloud VM, every Docker container, every CI runner, every Kubernetes node — they all run Linux. It's not optional. Linux fluency is the baseline skill that unlocks the entire DevOps stack.

# Core Linux skills every DevOps engineer needs

# 1. Navigate and manipulate files
ls -la /etc/nginx/
grep -r "server_name" /etc/nginx/

# 2. Manage services
systemctl status nginx
journalctl -u nginx --since "1 hour ago"

# 3. Inspect network
ss -tlnp | grep :80
  • chmod/chown: Control who can read, write, and execute files.
  • systemctl: Start, stop, enable, and inspect services.
  • journalctl: Read structured system logs — your first debugging tool.
  • ss / netstat: See what ports are open and what's listening.
  • cron / at: Schedule tasks without any orchestration tool.

LinuxAutomation

Automating DevOps Workstations

A fully automated workstation setup means you can rebuild your entire development environment in minutes. Never manually install tools again — script it once, version-control it, run it anywhere.

# workstation-setup.sh — bootstrap script
#!/bin/bash

TOOLS=("git" "curl" "docker.io" "ansible" "terraform")

for pkg in "${TOOLS[@]}"; do
  apt-get install -y $pkg
  echo "✓ Installed: $pkg"
done

# Install Terraform via HashiCorp repo
curl -fsSL https://apt.releases.hashicorp.com/gpg | \
  apt-key add -

Use Ansible for idempotent workstation automation — run it 10 times, same result every time:

  • Store dotfiles in Git: .bashrc, .vimrc, .gitconfig — all version-controlled.
  • Use roles: Separate roles for tools, terminal config, SSH setup.
  • Vault for secrets: SSH keys, tokens — encrypted in the repo.
  • Result: New machine fully configured in under 10 minutes.

LinuxHomelab

Building Labs on Old Hardware

You don't need expensive servers. An old laptop or a refurbished Dell Optiplex with 8–16GB RAM can run a full DevOps lab — Linux, Docker, Ansible, and a monitoring stack simultaneously.

# Check what resources you have
free -h          # RAM available
nproc            # CPU cores
df -h /          # Disk space
lscpu | grep "Model name"

# Minimal install Ubuntu Server = ~2GB RAM
# Docker + Compose = ~512MB extra
# Prometheus + Grafana = ~400MB extra
  • OS: Ubuntu Server 22.04 LTS — stable, well-documented, free.
  • Virtualization: KVM + libvirt for running multiple VMs on one machine.
  • Containers: Docker Compose for multi-service lab environments.
  • RAM target: 8GB minimum. 16GB for a comfortable multi-VM setup.
  • Networking: Use static IPs or local DNS (Pi-hole) for consistent lab addressing.

DevOps Homelab Architecture

A well-designed homelab mirrors production: a control node runs Ansible, target VMs simulate servers, Docker runs services, and a monitoring stack watches everything. Same tools, smaller scale.

Homelab Topology
──────────────────────────────
control-node  192.168.1.10
  ├── Ansible  (manages all nodes)
  ├── Terraform (provisions VMs)
  └── Git repos

server-01     192.168.1.11
  └── Docker + Compose apps

monitor-01    192.168.1.12
  └── Prometheus + Grafana

storage-01    192.168.1.13
  └── Samba4 + NFS
  • Safe failure: Break things without consequences. Learn from real errors.
  • GitHub portfolio: Every lab becomes a documented repo employers can see.
  • Cost: AWS charges by the hour. Your homelab charges once (electricity).
  • Speed: No cloud latency. Instant feedback loops for Ansible runs and Docker builds.

DockerBasics

What is Docker?

Docker packages your application and all its dependencies into a container — a lightweight, portable unit that runs identically on any machine. No more "works on my laptop" excuses.

# Pull and run an nginx container
docker run -d -p 80:80 --name web nginx

# List running containers
docker ps

# See logs
docker logs web --follow

# Shell into container
docker exec -it web bash
  • Image: Read-only template. Built from a Dockerfile. Stored in a registry.
  • Container: A running instance of an image. Ephemeral by default.
  • Registry: Docker Hub, AWS ECR, GHCR — where images are stored and pulled from.
  • Volume: Persistent storage that survives container restarts.
  • Network: How containers talk to each other and the outside world.
#03
DockerVMs

Docker vs Virtual Machines

VMs virtualise hardware — each gets its own OS kernel, eating GBs of RAM. Docker containers share the host kernel and start in milliseconds. For microservices, Docker wins on density and speed.

VM Stack vs Container Stack
──────────────────────────────
VM:  App → Guest OS → Hypervisor → Host OS → Hardware
Con: App → Docker Engine → Host OS → Hardware

Startup time:
VM  → 30–60 seconds
Con → <1 second

RAM per instance:
VM  → 512MB – 4GB (OS overhead)
Con → 5MB – 50MB (shared kernel)
  • Use VMs when: You need full OS isolation, different kernels, or legacy apps that require a specific OS.
  • Use Containers when: You're running microservices, need fast scaling, or want consistent dev/prod environments.
  • Use both: In Kubernetes — VMs (nodes) run container workloads. Best of both worlds.
#09
DockerStorage

Docker Volumes

Containers are ephemeral — kill one and its filesystem is gone. Volumes are the solution: persistent storage managed by Docker, surviving container restarts, removals, and recreations.

# docker-compose.yml — volume example
version: '3.9'
services:
  postgres:
    image: postgres:15
    volumes:
      - pgdata:/var/lib/postgresql/data
    environment:
      POSTGRES_PASSWORD: secret

volumes:
  pgdata:   # named volume = Docker managed
  • Named volumes: docker volume create mydata — Docker manages the path. Best for databases.
  • Bind mounts: Map a host path directly. Good for dev (live code reload). Risky in prod.
  • tmpfs: In-memory only. Fast, non-persistent. Good for secrets or temp data.
  • Backup tip: docker run --volumes-from db -v $(pwd):/backup ubuntu tar cvf /backup/db.tar /data
#10
DockerNetworking

Docker Networking

Containers need to communicate — with each other, with the host, and with the outside world. Docker provides network drivers for each use case: bridge, host, overlay, and none.

# Create an isolated network
docker network create app-net

# Run containers on the same network
docker run -d --network app-net --name api  myapi
docker run -d --network app-net --name db   postgres

# Containers resolve each other by name
# api container can reach: postgres:5432

docker network inspect app-net
  • bridge (default): Isolated network on the host. Containers get private IPs and resolve each other by name.
  • host: Container shares host's network stack. No isolation. Fastest performance.
  • overlay: Multi-host networking for Docker Swarm or distributed systems.
  • none: No networking. Fully isolated container for security-critical workloads.
#23
DockerBest Practices

Docker Mistakes Beginners Make

Most Docker problems come from a handful of repeated mistakes: running as root, storing state in containers, using latest tags in production, and ignoring .dockerignore.

# ❌ Bad Dockerfile
FROM ubuntu:latest
RUN apt-get update && apt-get install -y python3
COPY . .
CMD ["python3", "app.py"]

# ✅ Better Dockerfile
FROM python:3.11-slim          # pinned, minimal
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
USER appuser                   # non-root
CMD ["python3", "app.py"]
  • Using :latest tags: Unpredictable builds. Always pin image versions.
  • Running as root: Major security risk. Add a non-root USER in your Dockerfile.
  • No .dockerignore: Copies node_modules, .git, secrets into the image. Always add one.
  • Fat images: Use slim/alpine base images. Multi-stage builds for compiled apps.
  • Storing state in containers: Use volumes for databases and persistent data.

AWSCompute

What is AWS EC2?

EC2 (Elastic Compute Cloud) is AWS's virtual server service. You pick the CPU, RAM, and OS — AWS runs it. Pay per second. Scale from one instance to thousands in minutes.

# Launch EC2 via AWS CLI
aws ec2 run-instances \
  --image-id ami-0c55b159cbfafe1f0 \
  --instance-type t3.micro \
  --key-name my-key \
  --security-group-ids sg-12345 \
  --subnet-id subnet-abcde

# Connect via SSH
ssh -i my-key.pem ubuntu@PUBLIC_IP
  • AMI: Amazon Machine Image — the OS template. Choose Ubuntu, RHEL, Amazon Linux, etc.
  • Instance types: t3.micro (cheap, burstable), m5.large (balanced), c5 (CPU-optimised), r5 (RAM-optimised).
  • Elastic IP: Static public IP that persists across instance restarts.
  • Security Groups: Stateful firewall. Define inbound/outbound rules per instance.
  • User Data: Bootstrap script that runs on first launch — install packages, configure services.
#17
AWSNetworking

What is a VPC?

A Virtual Private Cloud is your own isolated network inside AWS. You define the IP ranges, subnets, routing tables, and internet access. Think of it as your private data centre in the cloud.

VPC: 10.0.0.0/16
├── Public Subnet:  10.0.1.0/24
│     ├── EC2 (web server)
│     └── NAT Gateway
│
└── Private Subnet: 10.0.2.0/24
      ├── EC2 (app server)
      └── RDS (database)

Internet Gateway → Public Subnet → NAT → Private
  • Subnet: Sub-division of the VPC. Public subnets have routes to the internet. Private do not.
  • Internet Gateway (IGW): The door between your VPC and the internet.
  • NAT Gateway: Lets private subnet instances reach the internet (for updates) without being reachable from it.
  • Route Table: Rules for where traffic goes. Associate with subnets.
  • NACL vs Security Group: NACLs are stateless subnet-level rules; SGs are stateful instance-level rules.
#18
AWSLoad Balancer

Load Balancer Explained

A load balancer distributes incoming traffic across multiple servers so no single instance gets overwhelmed. AWS ALB (Application Load Balancer) works at Layer 7 — routing by URL path, headers, and hostnames.

Client Request Flow
──────────────────────────────
Client
  ↓
ALB (port 443)
  ├── /api/*   → Target Group A (API servers)
  ├── /app/*   → Target Group B (App servers)
  └── /*       → Target Group C (Static servers)

Health Check: GET /health → 200 OK
Unhealthy instances → auto removed
  • ALB (Application): Layer 7. HTTP/HTTPS. Path and host-based routing. Best for web apps and microservices.
  • NLB (Network): Layer 4. TCP/UDP. Ultra-low latency. Best for gaming, IoT, high-throughput workloads.
  • CLB (Classic): Legacy. Don't use for new projects.
  • Target Groups: The collection of EC2s (or IPs) the LB sends traffic to.
#19
CloudNginxNetworking

Reverse Proxy vs Load Balancer

Both sit in front of your servers — but they serve different roles. A reverse proxy handles SSL termination, caching, and request routing. A load balancer distributes traffic across backend instances.

# nginx as reverse proxy
server {
  listen 443 ssl;
  server_name api.devriston.com.pk;

  location / {
    proxy_pass       http://localhost:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
  }
}
  • Reverse Proxy: Terminates client connections. Handles SSL, caching, compression, auth. Single backend target.
  • Load Balancer: Distributes connections across multiple backend targets. Focused on availability and throughput.
  • In practice: Nginx often serves as both — acting as reverse proxy per-service and round-robin across instances.
  • AWS combo: ALB (LB) → EC2s running Nginx (reverse proxy) → application processes.
#20
AWSArchitecture

High Availability Basics

HA means your system keeps running even when individual components fail. The core principle: eliminate single points of failure. Deploy across multiple Availability Zones. Use health checks and auto-recovery.

HA Architecture — 2 AZ Setup
──────────────────────────────
                  ALB
                 /   \
           AZ-1       AZ-2
            EC2         EC2
            RDS  ←──→  RDS
          (primary)   (standby)

Failover: automatic. RTO: seconds.
  • Multi-AZ: Deploy app servers in at least 2 Availability Zones behind a load balancer.
  • RDS Multi-AZ: AWS automatically maintains a standby replica. Failover in ~60 seconds.
  • Auto Scaling Groups: Replace failed instances automatically based on health checks.
  • Health checks: ALB health checks remove unhealthy targets. Route53 health checks for DNS failover.
  • Stateless apps: Store session data in Redis/ElastiCache, not in-memory, so any instance can serve any request.

TerraformIaC

Infrastructure as Code

IaC means your servers, networks, and cloud resources are defined in code files — not manually configured. This makes infrastructure reproducible, reviewable in Git, and deployable in minutes.

# main.tf — EC2 instance in code
resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"

  tags = {
    Name    = "devriston-web"
    Env     = "production"
    ManagedBy = "terraform"
  }
}
  • Reproducibility: Run the same code in dev, staging, and prod — get identical infrastructure every time.
  • Version control: Infrastructure changes go through Git PRs, code review, and audit history.
  • Disaster recovery: Rebuild your entire environment from code in minutes, not days.
  • Drift detection: Terraform detects when real infrastructure diverges from the declared state.
#04
AnsibleAutomation

What is Ansible?

Ansible automates server configuration over SSH — no agent required. Write a playbook in YAML, run it against 1 or 1000 servers, get the same result every time. Idempotent by design.

# install-nginx.yml
- name: Install and start Nginx
  hosts: webservers
  become: true
  tasks:
    - name: Install nginx
      apt:
        name: nginx
        state: present

    - name: Ensure nginx is running
      service:
        name: nginx
        state: started
        enabled: yes
  • Terraform: Provisions infrastructure (creates servers, networks, databases). Declarative state model.
  • Ansible: Configures what's inside the servers (installs software, manages users, deploys apps). Procedural YAML.
  • Together: Terraform builds the VM, Ansible configures it. Perfect combination.
  • Ansible strength: No agent. Works with any SSH-accessible machine — cloud, on-prem, bare metal.
#11
TerraformState

Terraform State

Terraform tracks what it has built in a state file (terraform.tfstate). This is how it knows what exists, what changed, and what to destroy. Never commit state to Git — use remote backends like S3.

# backend.tf — Remote state in S3
terraform {
  backend "s3" {
    bucket         = "devriston-tf-state"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "tf-lock"  # locking
    encrypt        = true
  }
}
  • Remote backend: Store state in S3 (AWS) or GCS (GCP). Never local files in a team environment.
  • State locking: Use DynamoDB to prevent two people from running terraform apply simultaneously.
  • Encryption: State files contain secrets. Always encrypt at rest and in transit.
  • terraform state commands: terraform state list, terraform state mv, terraform state rm — for surgical resource management.
  • Never edit manually: Direct state edits corrupt your infrastructure tracking. Use CLI commands instead.
#11b
TerraformMulti-Cloud

Why Terraform Matters

Terraform is cloud-agnostic. Write infrastructure for AWS today, replicate it on GCP or Azure tomorrow with minimal changes. 3000+ providers cover everything from DNS to Kubernetes to GitHub.

# Terraform workflow — 3 commands
terraform init     # download providers + modules
terraform plan     # show what will change
terraform apply    # execute the changes

# Plan output example:
+ aws_instance.web will be created
+ aws_security_group.web_sg will be created
Plan: 2 to add, 0 to change, 0 to destroy.
  • Terraform: HCL language. Multi-cloud. Massive community. 3000+ providers. The industry standard.
  • CloudFormation: AWS-only. YAML/JSON. No multi-cloud. Good if you're 100% AWS forever.
  • Pulumi: Write IaC in Python/TypeScript/Go. Great for developers who hate HCL.
  • Winner for DevOps engineers: Terraform. Every job posting, every open-source project, every cloud team.

CI/CDPipelines

CI/CD Pipeline Basics

CI (Continuous Integration) automatically builds and tests code on every commit. CD (Continuous Delivery/Deployment) automatically ships passing builds to staging or production. Together: faster, safer shipping.

# .github/workflows/deploy.yml
name: CI/CD Pipeline
on:
  push:
    branches: [main]

jobs:
  build-test-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build Docker image
        run: docker build -t myapp .
      - name: Run tests
        run: docker run myapp pytest
      - name: Deploy to production
        run: ./scripts/deploy.sh
  • Source: Git push triggers the pipeline. Feature branches, PRs, or merges to main.
  • Build: Compile code, build Docker image, resolve dependencies.
  • Test: Unit tests, integration tests, security scans (SAST), linting.
  • Staging deploy: Deploy to a pre-production environment for final verification.
  • Production deploy: Blue/green, canary, or rolling deployment to prod.
  • Notify: Slack/email on success or failure. Rollback on failure.
#12
GitCI/CD

Git Branching Strategy

A branching strategy defines how teams collaborate in Git. GitFlow uses long-lived branches. Trunk-based development uses short-lived feature branches merged to main frequently. For CI/CD, trunk-based wins.

# Trunk-based development workflow
git checkout -b feature/add-monitoring
# ... make changes ...
git add . && git commit -m "feat: add prometheus scrape config"
git push origin feature/add-monitoring

# Open PR → review → merge to main
# main merge triggers CI/CD pipeline
# Pipeline: test → build → deploy
  • Trunk-based: All developers commit to main (or short branches). CI runs on every commit. Fast, clean. Used by Google, Meta.
  • GitFlow: main + develop + feature + release + hotfix branches. Heavyweight but structured. Good for scheduled releases.
  • GitHub Flow: main + feature branches + PRs. Simple. Good for small teams with continuous deployment.
  • Best for DevOps: Trunk-based with feature flags. Ship often, control via flags, not branches.
#13
CI/CDGitHub ActionsJenkins

GitHub Actions vs Jenkins

Jenkins is a powerful, self-hosted CI server — but it requires maintenance, plugins, and a team to operate. GitHub Actions is managed, YAML-driven, and integrates natively with your repo. For most teams, Actions wins on simplicity.

Feature Comparison
──────────────────────────────────
                    GitHub Actions  Jenkins
Setup time          Minutes         Hours/Days
Infrastructure      Managed         Self-hosted
YAML config         Yes             Groovy DSL
Cost                Free tier       Server cost
Marketplace         10,000+ actions 1800+ plugins
Scaling             Automatic       Manual
  • Choose GitHub Actions if: Your code is on GitHub, you want zero infra overhead, and you don't need deep customisation.
  • Choose Jenkins if: You have complex, multi-team pipelines, need self-hosted runners for compliance, or have existing Jenkins investments.
  • Modern alternatives: GitLab CI, CircleCI, Drone CI — all worth knowing. GitHub Actions is the current default for open-source and startups.
#21
DockerAutomationReliability

Self-Healing Infrastructure

Self-healing means your infrastructure automatically detects and recovers from failures without human intervention. Docker health checks, restart policies, and AWS Auto Scaling are the building blocks.

# docker-compose.yml — self-healing config
services:
  api:
    image: myapi:latest
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
  • Process level: systemd restarts services; Docker restart policies restart containers.
  • Container level: Health checks detect failed containers; Compose/Swarm replaces them.
  • Instance level: AWS Auto Scaling replaces unhealthy EC2s; ALB stops routing to them.
  • Application level: Circuit breakers, retries, and timeouts prevent cascade failures.
  • Platform level: Kubernetes restarts crashed pods, reschedules on healthy nodes, and scales on load.

MonitoringArchitecture

Monitoring Stack Architecture

A production monitoring stack has three jobs: collect metrics (Prometheus), visualise them (Grafana), and alert on anomalies (AlertManager). Each component is purpose-built, composable, and open-source.

Monitoring Stack Flow
──────────────────────────────
Targets (EC2, Docker, Apps)
  ↓ expose /metrics endpoint
Prometheus  ← scrapes every 15s
  ├──→ Grafana      (dashboards)
  └──→ AlertManager (alerts)
            ↓
     Slack / Email / PagerDuty
  • Node Exporter: Linux system metrics — CPU, RAM, disk, network. Run on every server.
  • cAdvisor: Container metrics — per-container CPU, memory, and network from Docker.
  • Blackbox Exporter: HTTP/TCP probing — check if your endpoints respond correctly.
  • Postgres Exporter: Database metrics — queries, connections, cache hit rates.
  • Custom metrics: Instrument your application code to expose business metrics via /metrics.
#22
PrometheusGrafanaPromQL

Prometheus + Grafana Workflow

Prometheus stores time-series metrics and lets you query them with PromQL. Grafana connects to Prometheus as a data source and renders the queries as beautiful, actionable dashboards.

# PromQL — useful queries

# CPU usage % across all cores
100 - (avg by(instance)(rate(
  node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# RAM used %
(node_memory_MemTotal_bytes -
 node_memory_MemAvailable_bytes) /
 node_memory_MemTotal_bytes * 100

# HTTP error rate (5xx)
rate(http_requests_total{code=~"5.."}[5m])

Fastest way to run the full stack locally with Docker Compose:

  • Prometheus config: Define scrape_configs pointing at your targets (Node Exporter, app /metrics).
  • Grafana provisioning: Use provisioning YAML to auto-load datasources and dashboards — no manual clicking.
  • AlertManager: Define alert rules in Prometheus (alert.rules), route to AlertManager, configure receivers (Slack webhook, email SMTP).
  • Dashboard import: Grafana has 3000+ community dashboards. Import by ID — Node Exporter Full is dashboard #1860.
#30
LabsProduction

Lessons From Production-Style Labs

Real production experience teaches things no tutorial can. These are hard-won lessons from running actual services, dealing with real failures, and debugging systems that just stopped working at 2am.

# Lessons learned the hard way

# 1. Always check disk space first
df -h
# 2. Logs tell the story
journalctl -xe --since "10 min ago"
# 3. Check what's listening
ss -tlnp
# 4. Restart nothing until you understand why
# 5. Document EVERYTHING that went wrong
  • Monitoring before deployment: If you can't observe it, you can't debug it. Set up metrics before launch, not after the incident.
  • Idempotency matters: Scripts that break if run twice cause more problems than they solve. Write for repeatability.
  • Document the fix, not just the problem: Post-mortems that only describe what broke are useless. Capture root cause and remediation steps.
  • Staging is not prod: Test load, test network partitions, test what happens when a dependency goes down.
  • Smallest change wins: When debugging, change one thing at a time. Multiple simultaneous changes make root cause impossible to identify.

Most Important DevOps Skills

The DevOps job market is flooded with tool names but short on engineers who understand systems. The skills that actually get you hired — and keep you employed — are deeper than any single tool.

Tier 1 — Non-negotiable
  Linux fundamentals + bash scripting
  Networking (TCP/IP, DNS, HTTP, TLS)
  Git + version control workflows
  One scripting language (Python or Bash)

Tier 2 — Core DevOps
  Docker + container orchestration
  CI/CD pipeline design
  Cloud (AWS/GCP/Azure)
  IaC (Terraform/Ansible)

Tier 3 — Differentiators
  Observability + SRE practices
  Security (DevSecOps)
  • Go deep before wide: Master Linux before jumping to Kubernetes. Foundation skills compound.
  • Build, don't watch: A working homelab or GitHub lab beats 50 YouTube tutorials.
  • Document everything: A well-documented GitHub repo is a portfolio piece that speaks for you.
  • Read error messages: The ability to read and interpret stack traces and logs is the most underrated DevOps skill.

DevOpsLearning

How to Learn DevOps Effectively

Most people learn DevOps wrong — they watch tutorials and feel productive but can't do anything without the video paused. The only path that works: build real things, break them, fix them, document them.

Effective Learning Loop
──────────────────────────
1. Pick one concept     (e.g. Docker networking)
2. Read the docs        (not a tutorial)
3. Build a lab          (hands-on)
4. Break something      (intentionally)
5. Fix it               (debug the error)
6. Document on GitHub   (reinforce + portfolio)
7. Repeat               (next concept)
  • Official docs first: Docker docs, Terraform registry, AWS docs. Written by the people who built the tools.
  • GitHub — read real codebases: Real Ansible roles, Terraform modules, and GitHub Actions workflows teach more than any course.
  • Avoid tutorial hell: If you've watched 5 videos and written 0 code, you're not learning — you're consuming.
  • Time-box theory: 20% reading, 80% building. Most DevOps concepts click in 2 hours of hands-on work.

2026 DevOps Learning Path

  → Linux + bash + networking + Git

Phase 2: Containers + Cloud
  → Docker + AWS + Terraform

  • FinOps: Cloud cost optimisation is now a required skill, not an optional one.
#30a
DevOpsAutomation

Infrastructure Automation Workflow

A complete infrastructure automation workflow uses Terraform to provision resources, Ansible to configure them, GitHub Actions to orchestrate both, and Prometheus to watch the result. Each tool has one job.

Full Automation Pipeline
──────────────────────────────
Git push
  ↓
GitHub Actions
  ├── terraform plan  (review)
  ├── terraform apply (provision)
  ├── ansible-playbook (configure)
  └── smoke tests (verify)
  ↓
Production infrastructure
  ↓
Prometheus → Grafana (observe)
  • Plan before apply: Always run terraform plan in CI and require human approval before terraform apply in production.
  • Separate provision and config: Terraform provisions the VM; Ansible configures it. Mixing concerns causes fragility.
  • Smoke tests post-deploy: Run a simple HTTP check or service health verification before marking a deployment as successful.
  • Rollback plan: Know before you deploy how to revert. Terraform can destroy and recreate. Ansible can revert configs.

AnsibleBest Practices

Ansible Roles and Structure

Ansible roles are reusable, self-contained units of automation. Instead of one giant playbook, roles separate tasks, templates, handlers, and variables — making automation maintainable at scale.

Ansible Role Structure
roles/nginx/
  ├── tasks/main.yml     ← what to do
  ├── handlers/main.yml  ← on-change actions
  ├── templates/         ← Jinja2 config files
  ├── vars/main.yml      ← role variables
  ├── defaults/main.yml  ← default values
  └── meta/main.yml      ← dependencies
  • One role, one responsibility: nginx role installs nginx. It doesn't also configure your firewall.
  • Use defaults, not vars: Put overridable values in defaults/. Reserve vars/ for internal role constants.
  • Handlers for restarts: Use notify + handlers to restart services only when configuration actually changed.
  • Galaxy for external roles: Don't reinvent — use Ansible Galaxy for community roles. Pin the version.

DevOps Interview Preparation

DevOps interviews test both tools knowledge and systems thinking. Interviewers want to see that you understand why tools exist, not just how to run commands. Prepare for scenario-based questions.

Common Interview Question Types
──────────────────────────────
Scenario:
  "Our deployment broke prod. Walk me through
   your debugging process."

Design:
  "Design a CI/CD pipeline for a Node.js app
   deploying to AWS."

Concept:
  "Explain the difference between a container
   and a VM."

Practical:
  "Write an Ansible task to install nginx."
  • For scenario questions: Think out loud. State your assumptions. Start with observability (check logs, metrics).
  • For design questions: Draw the architecture (even in text). Name the tools and explain why you chose them.
  • For concept questions: Lead with "why it exists" before "what it does." Shows deeper understanding.
  • For practical questions: Write clean, idiomatic code. Add comments. Ask clarifying questions first.
  • Your homelab = your answer: For every question, tie your answer to something you actually built.

TerraformModules

Terraform Modules and Reuse

Terraform modules are reusable IaC components. Instead of copy-pasting VPC code across projects, write a module once, call it everywhere with different inputs. Same pattern as functions in programming.

# Calling a reusable VPC module
module "vpc" {
  source = "./modules/vpc"

  vpc_cidr     = "10.0.0.0/16"
  public_cidrs = ["10.0.1.0/24", "10.0.2.0/24"]
  environment  = "production"
  project      = "devriston"
}

# Reuse same module for dev:
module "vpc_dev" {
  source      = "./modules/vpc"
  environment = "development"
}
  • Single responsibility: One module = one infrastructure concern (VPC, EC2, RDS). Don't bundle everything.
  • Input variables: All environment-specific values as inputs. No hardcoded values inside modules.
  • Output values: Expose useful outputs (vpc_id, subnet_ids) for other modules to consume.
  • Version pin public modules: source = "terraform-aws-modules/vpc/aws" version = "5.1.0". Never use latest.

DockerProduction

Docker Compose Production Tips

Docker Compose is often dismissed as "just for dev" — but with the right configuration it runs production workloads reliably. Key: pinned versions, health checks, restart policies, and environment separation.

# Production-grade compose pattern
services:
  app:
    image: myapp:1.4.2       # pinned
    restart: unless-stopped
    env_file: .env.production   # no inline secrets
    healthcheck:
      test: ["CMD","wget","-qO-","http://localhost/health"]
      interval: 30s
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
  • Pin image versions: Never use :latest in production. Tag with exact versions.
  • Separate env files: .env.dev and .env.production. Never commit secrets.
  • Log rotation: Configure max-size and max-file to prevent disk exhaustion.
  • Resource limits: Use deploy.resources.limits to prevent one container starving others.
  • Healthchecks everywhere: Every long-running service needs a health check for auto-recovery.
